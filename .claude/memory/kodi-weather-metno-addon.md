User is building `weather.metno`, a Kodi weather addon for his Xbox (started 2026-06-03), because existing weather addons can't find small Norwegian places like Vuku/Verdal.

Key facts:
- Data: MET Locationforecast 2.0 + Sunrise 3.0 (api.met.no) — **no API key**, only an identifying User-Agent. Place search: Kartverket ws.geonorge.no/stedsnavn/v1 (JSON keys are Norwegian: `skrivemåte`, `representasjonspunkt.nord/øst`).
- **Gotcha:** api.met.no returns 403 for User-Agents containing placeholder domains like `example.com`.
- Architecture modeled on ronie's weather.multi (gitlab.com/ronie/weather.multi): settings format v1 with action-button RunScript, window 12600 properties (Current.*, Day0-6.*, Daily.N.*, Hourly.N.*).
- Dev loop without Kodi: `python tools/test_local.py` stubs xbmc modules and runs against live APIs; `tools/build_zip.py` builds the installable zip.
- Frost API (frost.met.no) deliberately not used — historical observations only.
- User communicates in Norwegian (bokmål).
- **User requirement:** everything embedded in the zip; only the forecast itself may be downloaded at runtime. So weather icons are bundled in `resources/icons/` (Kodi's CC BY-NC-SA default pack, codes 0-47 + na) — NOT the external `resource.images.weathericons.default` dependency (which isn't reliably present on Xbox and left tiles blank).
- **Estuary icon mechanism:** tile icons are built as `Skin.String(WeatherOutlookIcon.path)` + `FanartCode` + `Skin.String(WeatherOutlookIcon.ext)` (default `resource://resource.images.weathericons.default/` + code + `.png`). The addon overrides those skin strings via `Skin.SetString` on startup to point at its bundled icons. `OutlookIcon` properties are ignored by Estuary. Home-screen small widget uses skin's own `weather/small/<FanartCode>.png`, so FanartCode must stay 0-47.
- **Celsius/units:** temperature/wind/date are controlled by Kodi regional settings (Kodi converts legacy props itself), NOT the addon. User's Xbox was in US region (°F/mph). Fix is Settings → Interface → Regional → Temperature/Speed unit.
- User is on Windows 11; has Chrome with Claude plugin available for visual verification if needed.
- **CRITICAL — Estuary icon mechanism differs by Kodi version (learned the hard way):** On **Kodi 21 Omega**, Estuary builds forecast tile icons as `resource://resource.images.weathericons.default/` + `OutlookIcon` — the resource path is HARDCODED (no skin-string override) and it uses the `OutlookIcon` property (NOT FanartCode). So `OutlookIcon` MUST be a bare filename ("30.png") present in the bundled pack (codes 0-47 + na). Custom/Yr icons are IMPOSSIBLE in the Omega weather window (the `WeatherOutlookIcon.path` skin-string override only exists in Kodi 22 master Estuary). The `Day0..6` legacy items DO take a raw full path in OutlookIcon, but they're only shown when `Daily.IsFetched` is empty — and the daily widget hides entirely then, so unreachable. **Lesson:** for Estuary compatibility, weather addons must map conditions to 0-47 codes + use the bundled pack; set OutlookIcon to bare "<code>.png", FanartCode to "<code>", and Current.ConditionIcon to the full `resource://...default/<code>.png`.

- **The "0°C / feels like 0°" bug was STALE weather.multi data**, not a code bug. The user had BOTH weather.multi AND weather.metno installed; window 12600 properties persist in memory and are only overwritten, so multi's old Current.* (its "From NE at X km/h" wind format, etc.) lingered. Fix: uninstall weather.multi + physical restart → clean slate, real MET values (verified 14°C/Heavy Rain). LESSON: with multiple weather addons, stale window props mix; a restart clears them. local set_current was always correct.
